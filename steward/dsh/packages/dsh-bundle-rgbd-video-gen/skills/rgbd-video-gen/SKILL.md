# rgbd_video_gen novel-view synthesis

Use this skill only for rgbd_video_gen tasks. If the operator explicitly requests NovelAnything, use its skill and tools instead. This skill's preparation tool does not make rgbd_video_gen an authorized substitute for another named model; report missing capabilities rather than switching models.

Choose an input supported by the available `rgbd_video_gen_*` tools:

- Evidence throughout motion: call `ego_rgb_recording_start` at the requested FPS before navigation, use the existing prediction/receipt and `skill_run wait=false` tools independently, then `ego_rgb_recording_stop` and inspect status until succeeded. A recording that reaches max_frames before motion ends does not cover the whole route. Do not emulate fixed FPS with repeated model-driven camera calls. Reuse an already successful recording when supplied. Call `rgbd_video_gen_prepare_recording` with its recording_id and explicit targets; never replace requested whole-motion evidence with a final snapshot or `prepare_scene`. The recorder and preparation do not command motion or inference.

- Single-timestamp snapshot evidence (only when requested): capture with `ego_capture_cameras` if no capture was supplied, then call `rgbd_video_gen_prepare_scene` with its exact `manifest_path` and explicit `targets`. Omit `source_cameras` to use ONLY middle `head_camera` RGB, even when the capture contains other cameras. Additional sources require an explicit selection and matching dimensions and intrinsics; the existing `wide_camera` has different intrinsics and cannot be combined by this helper. Preparation reads only selected JPEGs and saves the complete scene. Submit its returned `scene_path` with the returned `num_source_views` and `max_target_views`; the default one-source/one-target scene has 2 frames and must be submitted with `num_source_views=1`. Do not use the server default of 6 for a prepared one-image scene.
- A supplied `rgbd_videogen_scene_v1` JSON file with inline evidence images: use `rgbd_video_gen_submit`.
- A ZIP with `scene.json` and relative image files: use `rgbd_video_gen_upload`, which uses server generation defaults.
- An explicitly requested service demo: use `rgbd_video_gen_demo`. `trajectory` follows the demo trajectory; `bev` requires an explicit view count and altitude scale and has no target ground truth.

Recording preparation retains every middle-camera RGB image and measured pose in `recording_manifest_path`. The remote API documentation and UI declare 1–8 source images per job. By default, use every frame for recordings of at most eight frames; otherwise uniformly select eight frames across the complete recording, including the first and last. No extra confirmation is needed for this default policy. `num_source_views` can override the uniform sample count, or `source_frame_indices` can explicitly select chronological samples for a batch. If the operator explicitly requires every recorded image to condition generation, explain the service limit and use an agreed alternative rather than describing a sample as all images. Batches produce separate predictions, not one prediction jointly conditioned on all frames. Inspect and report `recorded_frames`, `source_frame_indices`, `source_stamps` and `all_frames_used`. Preserving all local images does not mean all images reached the model. Do not put unused source images after the evidence block: the API treats those frames as targets. Submit exactly the returned scene_path, num_source_views and max_target_views.

Describe each target with `frame` plus either a rigid 4x4 `camera_to_frame` matrix OR the three vectors `position`, `look_at`, `up`, never both. `frame=reference` uses the middle camera's OpenCV axes (right/down/forward): the capture instant for snapshots, or the first recorded instant for recordings. `frame=gripper` uses gripper axes (forward/left/up). Positions and look-at points are metres; up is an image-up direction, not parallel to the viewing direction. Reuse middle-camera intrinsics. No target pose is selected implicitly: use the operator's requested viewpoint, or ask for the missing viewpoint.

For a gripper-forward view, use `targets:[{frame:"gripper",position:[0,0,0],look_at:[1,0,0],up:[0,0,1]}]`. For offsets, other directions or multiple novel views, specify those targets explicitly. Reference-frame targets do not require any gripper pose. Snapshot gripper targets require the embedded same-timestamp pose; do not mix in a later `ego_gripper_pose`. Recording preparation obtains a current gripper pose and relates it to all earlier evidence through the shared measured odometry frame.

Local scenes need 2–64 ordered frames, calibrated pixel intrinsics K and OpenCV camera-to-world poses in metres. The first `num_source_views` frames are evidence images (1–8, default 6); at least one later frame must supply a target pose, with an optional image for ground-truth comparison. Explicitly set `num_source_views` for fewer than 6 evidence images: one image plus one target needs 2 frames and `num_source_views=1`; three camera images plus one target need 4 frames and `num_source_views=3`. Use separate ordered reference-camera frames for the evidence images; three views within one frame do not count as three evidence frames. The model was trained on 6 evidence views, so other counts may reduce quality. Use JSON submission for small evidence sets; the ZIP tool uses server generation defaults. Do not pad or duplicate evidence to reach 7 frames, invent poses or treat an SLARM capture ZIP as this format.

In the robot Ego Harness, input paths resolve inside the robot workspace. Use supplied robot evidence and estimated poses. If these inputs are missing, report what is needed; a server demo is not a prediction of the robot's current surroundings. Do not obtain privileged simulator state through World tools or repository files.

The robot profile deliberately has no general file or shell tools, and delegated subagents inherit that restriction. Do not delegate scene file authoring or probe invented paths. Use the preparation tool directly; no plugin-source inspection or filesystem permission change is needed. Preparation does not submit a remote job. If the tool is unavailable, state the missing installed capability without escalating it as a robot hardware fault.

Check `rgbd_video_gen_capabilities`, submit with a stable `request_key`, then query `rgbd_video_gen_status`. Preserve the same key and options when retrying an uncertain submission. `queued` and `running` are pending; `failed` and `cancelled` stop the generation flow. Only `succeeded` permits reading `rgbd_video_gen_result` and selecting returned filenames for `rgbd_video_gen_download`. Submitted scenes, parameters and uploaded ZIPs are archived under inputs/rgbd_video_gen. Download returned artifacts under outputs/rgbd_video_gen/<job_id> and retain local_manifest_path; this manifest lists verified local paths, input archives and target RGB/depth mappings for downstream processes. Return its absolute path. No UI visualization is required. Report remote generation success and verified local downloads separately. Stopping local waiting does not cancel a remote job; use `rgbd_video_gen_cancel` for an explicit cancellation request.

Interpret RGB and depth as model predictions, not observations. Target camera `i` maps to frame `num_source_views+i`; inspect metadata instead of assuming six source views. Target PSNR requires target ground truth. Generated views do not update Ego-State or establish free space, grasp feasibility or a motion receipt. Robot motion continues to require the existing `ego_predict` and `skill_run` flow with actual observations.

Local loose RGB files distinguish `source_reconstruction_*.jpg` (input-view reconstructions) from `target_prediction_*.jpg` (requested novel views, numbered from zero). Select downloads by the remote `artifacts[].filename`, then report returned local paths, using manifest `targets` for RGB/depth pairs. Server ZIP entries and NPZ depth keys retain their original names. Do not count source reconstructions as additional requested targets.
